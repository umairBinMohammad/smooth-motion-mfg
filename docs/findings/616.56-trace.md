# Driver 616.56: first runtime trace

Ghost Recon Breakpoint (DX11), RTX 4060 Laptop, 2560x1440, Smooth Motion on,
tracer 0.1, 2026-11-10. The tracer loaded as `version.dll` beside `GRB.exe`
and all hooks installed.

## What NvPresent does per generated frame

1. On swapchain creation it loads 19 kernel modules (the `_fp8` network
   variants plus `downscale_kernel`, `depth_to_space_fp8`,
   `warp_coarse_kernel`). `main_kernel` is not loaded.
2. It records 25 kernel launches once into a **CUDA graph**
   (`cuStreamBeginCapture` .. `cuStreamEndCapture`) and from then on makes a
   single `cuGraphLaunch` per generated frame. Kernel parameters are baked
   into the graph; `cuLaunchKernel` is never called again. A new graph is
   recorded when the swapchain is recreated (seen for 2560x1410 and 2560x1440).
3. Order inside the graph: `downscale_kernel`, `conv1`..`conv8`, `conv_fused`,
   `conv_proj1`, `attn1` x4, `conv_proj2`, `attn2` x4, `depth_to_space`,
   `conv_out1`..`conv_out3`, `warp_coarse_kernel`.

Graph launches ran at 21 to 58 per second, one per rendered frame.

## The network works at a small resolution

**Correction (later trace):** the sizes below are for 2560x1440. At 1920x1080
the network ran at 768x432 with a 192x108 output, so its resolution scales
with the swapchain: the output grid is one tenth of the frame in each
direction. The statement below that cost does not depend on game resolution
is therefore wrong.

From the launch parameters:

| Stage | Resolution |
|---|---|
| `downscale_kernel` outputs | 1024x576 and 256x144 |
| `conv1`, `conv2` | 1024x576 |
| `conv3`..`conv5` | 512x288 |
| `conv6`..`conv8` | 256x144 |
| `conv_fused`, `conv_proj1`, `attn1` | 128x72 |
| `conv_proj2`, `attn2` | 64x36 |
| `conv_out1`..`conv_out3` | 256x144 |
| `warp_coarse_kernel` | reads a 256x144, 6-channel buffer; writes the full-size frame |

So the network's cost does not depend on the game's resolution, and its whole
result is a **256x144 image with 6 channels**. The only full-resolution work
is `warp_coarse_kernel`.

## The warp "scale" parameter is a resolution ratio

`warp_coarse_kernel` +48 held half floats (10.0, 10.0) at 2560x1440 and
(10.0, 9.79) at 2560x1410: output size divided by 256x144. The floats before
it are the reciprocals. It never changed with motion. Scaling it would resize
the picture, not move it in time, so the "scale one parameter" idea is dead.

## Where that leaves multi-frame

Still open, by a different route. One network pass yields a small 6-channel
field; a short kernel turns that field plus the two real frames into the
generated frame. If those 6 channels are motion vectors towards each real
frame plus blend weights, as the softmax and four texture fetches in
`warp_coarse_kernel` suggest, then a frame at any time t can be made by running
a second, modified warp with the vectors rescaled. The driver accepts PTX
text through the same `cuModuleLoadData` call, so that warp can be our own
kernel; no NVIDIA code needs patching for the generation step.

Cost would be one extra full-resolution warp per extra frame. The network,
which is the expensive part, still runs once.

Next: dump the 6-channel buffer and the 256x144 inputs for consecutive frames
(tracer 0.2, F9) and work out what each channel means.

## Consequences for the hook design

- Launch-time parameter edits are not possible after the first frame; the mod
  must act at graph level: add its own kernel launches after `cuGraphLaunch`,
  or intercept the capture and extend the graph.
- Device pointers of every intermediate buffer are visible in the captured
  launch parameters, including the network output and both real frames.

## Hand-over to the display (prototype 0.4.2 trace)

- **No hardware flip metering here.** NvPresent looked up 14 NVAPI interfaces
  on the RTX 4060 Laptop and neither `SetFlipConfig` (0xF3148C42) nor the
  flip-config caps query was among them. On this machine its pacer must be
  timing the generated and real frame in software.
- **D3D11 interop.** CUDA imports two 2560x1440 RGBA textures as
  `D3D11_RESOURCE` external memory and two `D3D11_FENCE` semaphores per
  swapchain, plus one CUDA-native 2560x1440 array.
- **Per real frame, one thread does:** wait on fence A, `cuGraphLaunch`
  (returns in about 0.05 ms; the work is asynchronous), signal fence B. The
  signalled value rises by 2 per frame.

So presenting extra frames means working on NvPresent's D3D11 side: an extra
copy and an extra DXGI Present per added frame, timed by us.
