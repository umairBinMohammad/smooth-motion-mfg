Inspected 2026-11-10 with `tools/inspect_nvpresent.py` and `tools/cubin_info.py`.
Nothing was loaded or run. Statements marked *inferred* come from names and
instruction patterns and still need a runtime check (phase 1).

## Hook surface: easy

`nvcuda.dll` is a normal import, by name, including `cuModuleLoadData`,
`cuModuleGetFunction`, `cuLaunchKernel`, `cuGraphLaunch`,
`cuStreamBeginCapture_v2` and the external-memory/semaphore interop calls.
Patching NvPresent's import table is enough to see every module load and
kernel launch. Note the CUDA graph calls: if NvPresent captures its
per-frame work into a graph, later frames will arrive through
`cuGraphLaunch`, not `cuLaunchKernel`. The tracer must watch both.

## Kernels: compiled only

37 fatbins, each with an sm_89 (Ada) and an sm_120 (Blackwell) cubin.
**No PTX anywhere.** The DLSS-G midpoint fix, which edits PTX text and lets the
driver recompile it, cannot be applied here. Any change to the maths has to be
made at launch time (different inputs or parameters) or by patching compiled
SASS.

Kernels by role (*inferred* from names):

| Stage | Kernels |
|---|---|
| Prepare | `downscale_kernel` |
| Network | `conv1`..`conv8`, `attn1`, `attn2`, `conv_fused`, `conv_proj1`, `conv_proj2`, `conv_out1`..`conv_out3`; every one also in an `_fp8` variant |
| Upsample | `depth_to_space` (and `_fp8`) |
| Synthesis | `warp_coarse_kernel` |
| Other | `main_kernel` |

- **`main_kernel` is not the interpolator** (unlike DLSS-G, where a kernel of
  that name is). 128 instructions, a 64-byte parameter block, only constants
  like 0.05, 0.1, 0.13, 0.16 and 1.0, and one surface store: it looks like the
  on-screen indicator box. *Inferred.*
- **`warp_coarse_kernel` builds the output**: 4 texture fetches, weights from
  `exp2(x * log2 e)` (softmax), one surface store. A 136-byte parameter block;
  the field at +48 is a pair of half floats that multiplies the sample
  coordinates. No 0.5 constant anywhere.

### What this means for multi-frame

DLSS-G passes the time position into its interpolation kernel; the unlock mods
only had to start using it. Here there is no sign of a time input: the network
appears to be trained to produce the midpoint directly, and the warp kernel
only applies what the network predicts. So strategy S1 (run synthesis again
at t = 1/3, 2/3) is not available as a parameter change.

The one opening: if the field at warp_coarse +48 scales the predicted
displacement, scaling it by 2t gives an approximate frame at time t from one
network pass (assumes straight-line motion between frames). If it is a
resolution ratio instead, this opening closes. The tracer settles it by
logging that field's value every frame.

## Pacing: built in, but batches of two

- Strings `HW Flip Metering Supported via %s queue`, `nvp.pacer`,
  `nvp.flipTracker`, `nvp.vblankTracker`, and the NVAPI flip-config interface
  ids `0xF3148C42` / `0x6194B19D` (3 code sites each): NvPresent already paces
  through the driver's hardware flip metering, the same mechanism Streamline
  uses for DLSS-G.
- The pacer's batch entry point (from C++ type info) is
  `NVP_Pacer::submitBatch(NVP_Swapchain*, unsigned, unsigned,
  std::array<NVP_Image*, 2>&, NVP_Semaphore*)`. The batch is a fixed array of
  two images: generated plus real. Multi-frame needs either a wider batch
  (patching NvPresent's code) or our own pacer in front of it.
- There is also a Reflex sync context (`NVP_Pacer::ReflexSyncContext`).

## Settings, logging and capture

- Settings come from the driver profile database (`NVIDIA Corporation\Drs\nvdrsdb*.bin`),
  the same store NVIDIA Profile Inspector edits. Per-API allow bits exist for
  DX11, DX12 and Vulkan.
- NvPresent has its own log file: `C:/NvPresent/logs/{APP_NAME}/nvp_log_{TIME}_pid{PID}.txt`.
  How it is switched on is unknown; most likely a hidden profile setting.
- It also has a frame capture feature writing to `C:\NvPresent\captures`
  (`NVP_Swapchain::prepareCapture`). Captured frames would let us compare
  generated frames offline.
- If Streamline's `sl.interposer.dll` is in the process, NvPresent steps aside
  for D3D11 games ("the app keeps DLSS-G").
- NvPresent creates its own D3D12 queues (`NVP_Device_CopyCommandQueue`,
  `NVP_FGX_ComputeCommandList`, `NVP_Pacer_CommandList`), so its output path
  is D3D12 even for DX11 games.
